# ADR-006：以搜索 API 为核心、CLI 为入口包装，暂缓 MCP

**日期：** 2026-07-15  
**状态：** 已接受

## 背景

下一阶段需要为导游 Agent 增加网络搜索能力，用户以国内网络环境为主，同时会查询偏门的人文地理知识和非亚洲地区内容。当前已经使用豆包搜索 Custom 版完成真实接口测试：接口连通性和候选结果召回基本可用，但仍出现指定域名下主题跑偏、虚构地点返回无关结果、来源质量混杂等问题。

项目后续还需要提供一个 CLI（命令行工具）入口，便于手动测试、批处理和独立调试。因此需要先确定运行时调用边界，避免 Agent 直接启动 CLI 子进程或重复实现搜索逻辑。

## 决策

以豆包搜索 Custom API 作为搜索能力的唯一底层数据入口；在项目内抽取共享的 `src/search/`（搜索服务）层，由 LiveKit 工具和 CLI 分别调用。第一阶段暂不把 MCP（Model Context Protocol，模型上下文协议）作为主接入方式；未来确有外部 MCP 客户端需求时，再为同一搜索服务增加 MCP 适配层。

```text
豆包搜索 Custom API
          ↓
src/search/（请求、清洗、相关性和来源过滤）
       ↙                 ↘
src/tools/（LiveKit）     src/cli/（命令行）
```

## 原因

- API 适合 Agent 服务端直接调用，返回结构化 JSON，不需要启动子进程，延迟、超时、重试和错误处理更容易控制。
- CLI 适合开发者手动验证和后续命令行集成，但不应成为实时语音 Agent 的运行时依赖。
- 共享 `src/search/` 可以保证 Agent 和 CLI 使用相同的结果清洗、来源过滤和无结果保护逻辑。
- MCP 是工具暴露协议，不是搜索质量控制方案；在当前 Node.js Agent 中先使用 LiveKit 自定义工具更直接。未来增加 MCP 时只新增适配层，不改变搜索核心。
- API Key 只由服务端配置层读取，CLI 也通过环境变量传入，不通过命令行参数传递。

## 影响

- `src/search/` 成为搜索 API、结果标准化、来源过滤和相关性判定的共享边界。
- `src/tools/` 只负责把搜索服务包装成 LiveKit Agent 可调用的工具，不直接实现 HTTP 协议。
- `src/cli/` 只负责参数解析、输出格式和退出码，不复制搜索业务逻辑。
- Agent 不得通过 `child_process` 启动 CLI 来完成搜索。
- CLI 必须支持结构化 JSON 输出，错误信息写入 stderr，便于脚本和人工使用。
- 搜索 API Key 纳入 `src/config/` 的 Zod（运行时 Schema 校验库）配置边界，不能散落读取 `process.env`。
- 搜索结果必须经过实体相关性、来源质量、去重和无结果判定后，才能交给 LLM（大语言模型）生成回答。

## 不在此决策范围内

- 当前不实现搜索 Agent、事实核验模型或第二个 LLM；这些由后续 Spec 单独评估。
- 当前不实现 MCP Server，也不承诺所有外部 MCP 客户端兼容。
- 当前不切换豆包搜索 Global 版，不同时维护多个搜索供应商。
- 当前不实现模拟器遥测、机场数据库、天气或其他外部业务工具。
