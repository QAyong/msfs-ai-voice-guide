# ADR-002：最小 Provider 装配与延迟抽象

**日期：** 2026-07-15  
**状态：** 已接受

## 背景

LLM、STT 和 TTS 供应商尚未选择，但项目必须能在以后替换或新增 Provider。过早实现通用插件框架、注册表或多层工厂会增加第一版成本，也无法基于真实 Provider 差异设计可靠接口。

## 决策

在 `src/providers/` 集中创建首个 Provider 实例；第一版仅实现一个已选组合。只有出现第二个真实 Provider 需求时，才从现有实现提炼最小内部接口或选择逻辑。

## 原因

集中装配使 Provider SDK、模型名和认证细节不泄漏到会话与导游逻辑中；延迟抽象避免为假设的扩展点重复造轮子。

## 影响

- `src/agent/` 只接收已创建的能力实例，不能包含供应商专有初始化代码。
- Provider 选择、必需环境变量和模型名由 `config` 与 `providers` 配合处理。
- 抽象必须由至少两个实际实现的共同需求驱动，且形状以 LiveKit 当前类型为准。
- 未来新增工具不能借用 Provider 层承载业务逻辑，应放入 `src/tools/`。

## 不在此决策范围内

- 第一套 LLM、STT、TTS 的选型结论。
- 模型质量、成本和延迟的评测方法。
- 多 Provider 自动故障切换。
