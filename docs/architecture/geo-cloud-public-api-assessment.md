# 把 Geo Cloud 对外提供为公开 API 的评估

> 评估日期：2026-09-25
> 状态：**待服务端核实**（本文档的"待确认清单"需要 SSH 上机后逐条填写）
> 相关文档：[外部地理模块架构](../../native/msfs-cli/docs/architecture/external-geo-module.md)、[ADR-003](../../native/msfs-cli/docs/adr/adr-003-external-geo-cloud.md)、[开源准备清单](../opensource-readiness.md)

## 结论

**技术上可行，而且现有契约几乎可以直接当公开 API v1 用。** `POST /v1/location-context` 的请求/响应结构、错误码、来源标记（`_meta.source_map`）都已经是稳定契约，不需要为"对外开放"重新设计协议。

真正的工作量不在协议，而在三件事：**① 鉴权模型要从「一个共享静态 key」升级为「多消费者可撤销配额」；② 数据许可要逐字段过一遍，其中 MSFS POI 是硬约束；③ 滥用防护与可观测性从零开始。**

## 一、现状与目标的差距

| 维度 | 现在（自用） | 对外 API 需要 | 工作量 |
| --- | --- | --- | --- |
| 鉴权 | 单个共享 key，`X-MSFS-Geo-Key` 头写死比对；key 还被打进安装包 | 多消费者 key：可签发、可撤销、可轮换、可标记用途 | 中 |
| 配额 | 无。客户端侧只有 1–10 秒超时 | per-key 配额 + 令牌桶，返回 `429` 与 `Retry-After` | 中 |
| 滥用防护 | 无。key 只有一个，泄漏即全泄 | 注册/申请流程、异常速率检测、必要时 WAF | 中高 |
| 可观测性 | 未知（待核实） | per-key 用量、错误率、P95 延迟、缓存命中率 | 中 |
| 契约文档 | **仓库内无 OpenAPI/Swagger 文件** | OpenAPI 3.x + 文档站 + 版本策略 + 变更日志 | 低（契约定型，只需成文） |
| 错误语义 | 已有稳定错误码（`EXTERNAL_GEO_*`） | 直接沿用，补 HTTP 状态码映射表 | 低 |
| 浏览器调用 | 无 CORS | 若要让网页调用需配 CORS 与公开方来源白名单 | 低 |
| 状态页/SLA | 无 | 状态页 + 明确的"尽力而为、无 SLA"声明 | 低 |

## 二、数据许可：这是硬约束，必须先过

| 数据 | 许可 | 能否对外提供 API |
| --- | --- | --- |
| Natural Earth（15 图层） | 公有领域 | ✅ 可以，无需署名（建议仍署名） |
| GeoNames | CC-BY 4.0 | ⚠️ 可以，**必须署名**（文档 + 响应元数据） |
| OSM / Nominatim | ODbL + Nominatim 使用政策 | ⚠️ 有条件的可以。**公共 Nominatim 实例的 1 req/s 与"禁止大规模使用"政策不允许承载对外服务**，必须自托管；ODbL 对衍生数据库有同许可要求 |
| **MSFS POI** | 微软 / Asobo 游戏数据 | ❌ **对外再分发风险最高**。建议公开 API 先**不返回 `game_poi`**，或在获得书面许可前仅对本项目客户端开放该字段 |
| 机场/导航设施 | MSFS `facilities` 原生接口 | ✅ 由客户端本机读取，不经服务器，无再分发问题 |

结论：**把 API 对外之前，`natural` 和 `administrative` 可以先开；`game_poi` 应该单独决策。** 好在现有响应已经按字段分域（`administrative` / `natural` / `game_poi` / `place`），技术上很容易按调用方身份裁剪字段。

## 三、成本模型

- **主要成本是 PostGIS 空间查询的 CPU，不是带宽**：单次响应很小（几百字节到几 KB），请求体更小。
- **缓存命中率决定一切**：飞机在同一区域盘旋会产生大量近似坐标的重复查询，按 `(lat, lon, detail, locale)` 网格化缓存能显著削峰。ADR-003 已把缓存列为云端职责，需核实是否已实现。
- **自托管 Nominatim 是隐藏成本**：如果要对外提供 `place` 字段，Nominatim 需要独立实例（磁盘与内存开销远大于 PostGIS 本身）。可行做法是 `detail=full` 限流更严，或对外默认只给 `coarse`/`auto`。

## 四、三种对外形态

| 形态 | 做法 | 适合场景 | 风险 |
| --- | --- | --- | --- |
| A. 匿名低配额 | 无 key，按 IP 限流（例如 30 次/分钟） | 扩大生态影响、让插件作者零成本试用 | 会被扫描器刷；需要严格的 IP 限流与熔断 |
| B. 申请制 key（推荐起步） | 免费 key 申请（表单/Issue/Discord），per-key 配额 | 当前模式的自然延伸，可控 | 需要人工或半自动的发放流程 |
| C. 付费 / 赞助 key | 计费系统 + 分档配额 | 覆盖服务器成本 | 引入结算、退款、税务复杂度；对开源社区项目性价比低 |

**推荐路径**：先做 B（申请制 + 文档 + OpenAPI），把 A 作为只读的"试试看"入口（极低配额）；C 在出现明确需求前不做。这样既能给别人用，又不至于让服务器变成公共资源。

## 六、与开源的关系

把 Geo Cloud 对外提供 API 和把项目开源是**互补**的两件事：

- 开源服务端（PostGIS + 导入脚本 + 这份 API 契约）能让别人自建，你不必承接所有用户的成本；
- 你自建的公开实例则成为"零配置就能用"的入口，降低别人试用的门槛——这通常是 MSFS 这种模组生态里最有效的推广方式；
- 两者的接口契约必须一致，也就是现有的 `POST /v1/location-context`，所以先把它写成 OpenAPI 是共同的前置工作。

**顺序建议**：先开源服务端 → 再把线上实例按形态 B 对外开放 → 最后视需求加匿名配额或付费档。
