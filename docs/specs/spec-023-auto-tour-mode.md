# Spec-023：探索结果 AI 讲解

**日期：** 2026-08-19<br />
**状态：** 待审阅<br />
**建议优先级：** P0，作为探索模式完成后的增量能力<br />
**关联规格：** [Spec-015 用户触发的探索模式](spec-015-user-triggered-explore-mode.md)、[Spec-022 游戏内 POI 读取](spec-022-game-poi-reading.md)

## 1. 产品定义

用户在探索面板完成一次探索后，点击“讲解”按钮。一个专门的 AI 讲解角色读取 `ExploreService` 已保存的本次探索快照，生成一段中文或英文导游式讲解，并复用当前 TTS 配置进行播放。

讲解 AI 的事实输入只来自探索流程已经产出的内容。点击讲解后不重新访问百科网页、不读取来源网页正文，也不调用额外的百科内容提取服务。

这段讲解不是独立的旁白播放器，而是当前聊天会话中的一条**助手消息**：

- 讲解文字显示在聊天面板；
- 讲解音频通过现有 LiveKit/TTS 音频管线播放；
- 讲解结果写入当前 Agent 会话上下文；
- 用户随后可以围绕刚才的讲解继续提问。

本需求中的“自动”仅表示 AI 自动组织一段讲解，不表示后台自动触发、自动监控位置或沿途连续播报。

## 2. 用户流程

1. 用户在聊天面板点击“探索”。
2. 应用按照 Spec-015 生成本次探索结果，包括探索主题、探索生成的导览介绍、主题说明和来源卡片。
3. 探索结果展示完成后，界面提供“讲解”入口。
4. 用户点击“讲解”。
5. 应用提交本次探索结果的标识和讲解范围。
6. 讲解 AI 使用已保存的探索快照生成一段导游式讲解，不重新读取来源网页。
7. 讲解文字作为 assistant 消息写入聊天面板和当前会话上下文。
8. 同一条 assistant 消息通过当前语言和 TTS 音色播放。
9. 播放完成后，用户可以继续文字或语音对话。

### 2.1 讲解范围与用户输入竞合

第一版确定使用“讲解本次探索总结”作为本次能力。探索结果面板只提供一个全局“讲解本次探索”按钮，不在每个百科卡片上增加独立讲解按钮。按单个主题讲解可作为后续扩展。

讲解与用户语音输入必须遵循单一音频回合规则：

- 用户正在按住说话、连续对话或提交文字时，不能同时开始讲解；
- Agent 正在处理或播放普通回答时，讲解按钮显示忙碌状态，不启动新的讲解；
- 讲解播放期间，用户开始真实语音输入时，用户输入优先，当前讲解应被取消或停止；
- 用户只是在文字框中编辑草稿时，不必立即停止讲解；用户真正发送文字时，按单一回合规则处理；
- 已经生成并写入聊天上下文的讲解消息，即使播放被停止，也应保留在聊天记录中；
- 尚未生成稳定 assistant 消息的任务被取消时，不得写入半成品消息。

## 3. 第一版行为

### 3.1 讲解输入

后端根据 `explorationId` 找到本次探索结果，不接受 Renderer 直接提交任意完整结果作为事实来源。第一版讲解范围是整个探索结果的简短总结；`topicId` 只作为后续单主题讲解的预留字段。

讲解 AI 第一版只使用 `ExploreService` 保存的探索快照中的以下信息：

- `exploreResult.introduction`，即探索流程已经生成的导览介绍；
- 各主题的 `title`；
- 各主题的 `reason` 或主题说明；
- 探索结果契约中已经存在的主题摘要或描述字段（如果有）；
- 当前探索请求的 `locale`。

`explorationId` 只用于定位和校验快照，不是事实内容。百科、视频来源卡片的标题、站点名、URL 和其它元数据只用于来源窗口展示、主题关联和用户点击查看，不作为讲解 AI 的事实上下文。讲解服务不得根据这些元数据自行补写网页事实，也不得重新读取当前 MSFS 或其它外部上下文。

视频卡片第一版不作为自动讲解的事实输入。视频仍可由用户在探索结果中手动打开。

讲解请求不调用百科 Provider，也不依赖百科卡片是否能打开。只要探索快照中存在 `introduction`、主题标题或主题说明，就可以基于这些已获取内容生成讲解；如果快照没有可用的探索内容，则返回“当前探索内容不足，无法生成讲解”，不能通过抓取来源网页或模型猜测来补足。

### 3.2 讲解输出

讲解 AI 输出一段适合直接口播的导游式讲解：

- 中文目标约 300～500 个汉字，硬上限约 600 个汉字，适合约 1.5～2.5 分钟口播；
- 英文目标约 150～250 个单词，硬上限约 300 个单词，适合约 1.5～2.5 分钟口播；
- 内容结构为“开场定位 → 地点或主题背景 → 2～3 个重点 → 已有探索内容中的故事或知识 → 简短收尾”；
- 不输出 Markdown、URL、来源卡片、推荐问题或长列表；
- 不要求用户再次输入问题；
- 只使用传入的探索快照内容，不声称读取了未提供的事实；
- 信息不足时使用受限的概览式表达，不能编造具体地名、年代、人物或数据。

讲解文本生成成功后，必须先形成一条稳定的 assistant 消息，再进入播放流程。TTS 失败时，文字消息仍保留在聊天中，并给出可行动的失败提示。

## 4. 会话与聊天上下文

### 4.1 消息归属

讲解结果应作为当前 AgentSession 的 assistant turn 处理，而不是只在 Renderer 中追加一条展示消息，也不是只调用一次独立 TTS。

建议保留以下内部元数据：

```text
role: assistant
origin: explore_narration
explorationId: <本次探索 ID>
topicId: <主题 ID，可选>
```

用户界面可以将它显示为普通 AI 消息，也可以增加轻量的“探索讲解”标记。内部元数据用于诊断、去重和后续上下文处理，不改变普通 assistant 消息的对话语义。

### 4.2 上下文一致性

讲解文字必须同时进入：

1. 聊天面板的消息历史；
2. Agent 当前会话的 `ChatContext`；
3. 后续需要时用于构建最近对话的消息集合。

不能只更新 `desktop/renderer/src/session-messages.ts` 或本地 UI 状态。否则用户可以看到讲解，但后续 Agent 无法理解“刚才讲过的内容”。

隐藏的“点击讲解”控制事件不应被渲染为一条虚假的用户消息。可在 Agent 内部作为控制意图处理，但最终必须产生一条真实的 assistant 消息。

## 5. 后端职责与模块边界

```text
ExploreService
    负责探索主题、百科卡片和探索结果

ExploreNarrator
    负责把已保存的探索快照转换成导游式讲解文本，不重新获取来源内容

Conversation Bridge
    负责把讲解文本作为 assistant turn 写入当前 Agent 会话

现有 TTS / LiveKit 音频管线
    负责使用当前语言、音色和会话输出播放讲解
```

### 5.1 ExploreService

- 继续负责 Spec-015 的探索规划和来源发现；
- 探索成功后生成可引用的 `explorationId`；
- 保存本次探索结果，至少覆盖当前桌面会话；
- 不负责自动播放讲解；
- 不因用户移动或应用启动而触发讲解。

现有 [desktop/main/explore-controller.ts](../../desktop/main/explore-controller.ts) 可以继续负责探索结果缓存和展示，但讲解请求必须通过独立的讲解入口处理，不复用其对话变化和位置变化触发逻辑。

### 5.2 ExploreNarrator

建议新增独立的探索讲解服务，例如：

```text
src/explore/narrator.ts
```

它是一个专门的 LLM 角色，不是第二个 LiveKit AgentSession，也不维护独立的长期聊天历史。

它负责：

- 校验探索结果快照和讲解范围；
- 从探索快照中选择已经生成的 `introduction`、主题和主题说明；
- 使用当前 locale 构建讲解提示词；
- 生成结构化的导游式讲解结果；
- 不调用百科 Provider、不读取任意来源 URL 或网页正文；
- 在超时、取消或输入不足时返回稳定错误。

### 5.3 Conversation Bridge

讲解文本生成后，需要由当前 Agent 会话接收并发布为 assistant turn。具体调用方式必须按当前安装的 LiveKit Agents 类型定义核验，不能凭记忆假设 API。

Conversation Bridge 不应：

- 创建第二个 LiveKit 房间或第二个 AgentSession；
- 直接操作 SimConnect 或 MSFS CLI；
- 只调用独立 TTS 而不写入会话上下文；
- 将讲解伪装成普通用户输入。

## 6. 前端设计

### 6.1 入口位置

第一版继续沿用当前探索流程，不在设置页增加开关，也不在聊天标题栏新增第二个“讲解”按钮：

1. 聊天面板标题栏现有的“探索”按钮负责发起探索；
2. 探索完成后，应用继续使用现有的 `explore.result` Companion Source Window 展示主题和来源卡片；
3. “讲解本次探索”按钮放在该探索结果的顶部摘要区域；
4. 讲解完成后，内容回到聊天面板，来源窗口保持当前探索结果，不自动跳转百科页面。

对应的现有实现落点是：

- `desktop/renderer/src/main.tsx` 的 Assistant View 继续负责发起探索；
- 同文件的 Source View 中现有 `.explore-route` 摘要区增加讲解动作；
- `desktop/main/index.ts` 继续负责 Companion Source Window 生命周期和 IPC；
- 不新增第二个探索窗口或独立的讲解页面。

### 6.2 探索结果摘要区

在现有探索结果摘要区的标题行中增加一个全局动作：

```text
[探索概览]                         [讲解本次探索]
已整理 N 个来源
```

设计规则：

- 按钮作用范围是整个探索结果，不绑定单个卡片；
- 使用现有 Phosphor 图标库中的扬声器或播放图标，并保留清晰的文字标签；
- 生成中显示加载状态，播放中显示“停止讲解”；
- 不把讲解按钮嵌套在百科或视频来源卡片内部；
- 不自动打开或切换来源网页；
- 讲解按钮不改变现有来源卡片的点击行为。

现有 `exploreIntroduction` 可以继续作为探索结果的文字概览显示，但它不是自动播放内容。用户必须点击“讲解本次探索”后，才生成并播放新的 assistant 讲解。

### 6.3 按钮状态和反馈

探索面板需要订阅独立的讲解状态，不把讲解状态复用为 `exploring`：

```text
idle
generating
speaking
completed
busy
cancelled
failed
```

建议行为：

- `idle`：显示“讲解本次探索”；
- `generating`：按钮禁用，显示进度图标和“正在准备讲解”；
- `speaking`：按钮变为“停止讲解”，允许取消当前播放；
- `completed`：显示“再次讲解”，允许用户有意重复播放；
- `busy`：提示普通聊天或用户语音回合正在进行；
- `cancelled`：恢复可操作状态，不显示错误；
- `failed`：显示短错误和“重试”动作。

状态提示应出现在摘要区按钮附近，不使用全局弹窗打断用户阅读来源。讲解成功后可以显示“已发送到聊天”的短状态，但不在探索窗口重复渲染完整讲解文本。

### 6.4 聊天面板中的讲解消息

讲解完成后，聊天面板按普通 assistant 消息渲染，不新增第二套消息列表：

- 文字进入现有 `useSessionMessages()` 消息流；
- 主聊天窗口沿用现有跟随最新消息的滚动逻辑；
- 用户可以直接在文字输入框或语音输入中继续追问；
- 可使用非常轻的“探索讲解”来源标记，但不能显示为用户消息；
- 讲解文本不应被包裹成来源卡片，也不应覆盖现有聊天气泡样式。

讲解内容目标约 300～500 个汉字，硬上限约 600 个汉字；这只是生成内容的长度约束，不是讲解专用的气泡折叠阈值。

### 6.4.1 聊天面板通用长消息折叠

本需求明确要求在聊天面板新增通用的长 assistant 消息折叠能力。它不是探索讲解的专属组件，普通回答和探索讲解都必须复用同一套逻辑。

第一版规则如下：

- 只对 assistant 消息启用，user 消息保持现有展示；
- 以 Markdown 渲染后的实际高度作为判断依据，不按原始字符数截断；
- 第一版折叠预览最多显示约 6 行正文，约 108px 内容高度，具体值允许在目标窗口人工验收时微调；
- 超过预览高度的 assistant 消息默认显示折叠预览，短消息不显示额外的展开控制；
- 折叠状态按消息 `id` 保存在 Renderer 的展示状态中，不写入消息契约、不写回 Agent `ChatContext`，也不跨会话持久化；
- 展开后显示完整 Markdown 内容，收起后恢复预览；预览不得通过字符串截断，以免破坏 Markdown、链接或换行结构；
- 使用聊天面板统一的展开/收起按钮、图标和无障碍语义，包括正确的 `aria-expanded`；
- 折叠或展开不停止 TTS，不改变消息已经进入聊天历史和上下文的事实，也不影响来源预览按钮；
- 普通回答和 `origin: explore_narration` 消息的折叠外观、阈值和交互必须一致。

当前 `desktop/renderer/src/main.tsx` 已通过 `useSessionMessages()` 和 `MessageMarkdown` 统一渲染 assistant 消息，现有“收起”主要针对整个助手窗口。实现时应在现有 `.guide-reply` / `.bubble.markdown-content` 消息渲染层增加通用折叠状态和控制，必要时抽取为可复用的 `CollapsibleAssistantMessage` 组件；`MessageMarkdown` 继续负责 Markdown 渲染，`session-messages.ts` 继续保存完整消息文本。Spec-023 不新增讲解专用消息模型或专用气泡组件。

来源窗口可以保持打开。用户在来源窗口阅读时，聊天窗口收到新 assistant 消息仍应遵循现有未读消息和滚动规则，不强制抢夺窗口焦点。

### 6.5 与用户语音输入的前端竞合

前端可以根据已知状态提前禁用按钮，但后端/Agent 的回合协调仍是最终判断：

- 用户正在按住说话或连续对话时，按钮不可用；
- Agent 正在思考、调用工具或播放普通回答时，按钮显示忙碌；
- 讲解播放时用户开始真实语音输入，前端发送取消并让用户回合优先；
- 用户只编辑文字草稿时不停止讲解；
- 用户发送文字时，前端按统一回合策略取消讲解或显示忙碌，不能并行播放；
- 取消后已经写入聊天的讲解消息保留，未提交的生成结果丢弃。

Source Window 不能直接读取 Assistant View 内部的麦克风 Ref 或 Agent 状态 Ref。需要通过共享的讲解状态事件或主进程转发状态，避免两个 Renderer 各自维护一套冲突状态。

### 6.6 IPC 和跨窗口通信

建议在现有探索 IPC 旁增加最小白名单 API：

```text
requestExploreNarration(request)
cancelExploreNarration()
onExploreNarrationState(callback)
```

其中：

- Source Renderer 只提交 `explorationId`、locale 和固定的 `scope: exploration_summary`；
- Main 进程校验请求来源必须是 Source Window；
- Main 进程校验 `explorationId` 必须对应当前展示的 `explore.result`；
- Renderer 不提交来源网页正文、百科内容、任意 URL 或任意 assistant 文本；
- Main 和讲解服务只根据 `explorationId` 读取并校验已保存的探索快照，不在讲解请求中追加外部来源内容；
- 讲解状态同步到 Source Window，assistant 消息和音频状态通过现有会话链路进入聊天面板；
- Source Window 关闭、探索结果切换或新探索完成时，旧讲解状态必须失效。

当前 `shared/source-preview.ts` 的 `explore.result` 预览只携带 `result`。实现前需要为预览或其外层状态补充稳定的 `explorationId`，推荐扩展 Companion Preview 外层契约，而不是把缓存身份混入主题标题或 `generatedAt`。

### 6.7 可访问性和布局

- 讲解按钮必须有本地化可见标签、`aria-label` 和悬停提示；
- 加载、播放、失败状态必须有 `role="status"` 或 `role="alert"` 的可读文本；
- 按钮在窄窗口中不能挤压探索标题和来源数量，必要时让按钮独占下一行；
- 不使用只有颜色变化的状态表达；
- 讲解按钮与现有来源卡片保持相同的键盘焦点和点击反馈；
- 不新增嵌套卡片层级，不改变来源窗口现有阅读、缩放和导航控件。

## 7. 共享契约建议

建议新增独立的讲解契约，不把讲解状态混入 `guide.sources`：

```text
shared/explore-narration-contracts.ts
```

建议至少包含：

```text
exploreNarrationRequestSchema
exploreNarrationResultSchema
exploreNarrationStateSchema
exploreNarrationErrorSchema
```

请求至少需要：

```text
explorationId
scope: exploration_summary
locale
topicId（后续单主题讲解预留，可选）
```

结果至少需要：

```text
narrationId
explorationId
scope
sourceTopicIds
topicId（后续单主题讲解预留，可选）
text
createdAt
```

如需在消息中标识来源，可以增加 `origin: explore_narration`，但不要把讲解结果包装成 `guide.sources`。 `guide.sources` 仍只表示某次普通导游回答使用的搜索证据。

## 8. 播放和并发控制

### 8.1 单次请求

同一桌面会话同时只允许一个探索讲解请求处于生成或播放状态。

按钮状态至少包括：

```text
idle
generating
speaking
completed
cancelled
failed
```

点击后应立即禁用重复提交，后端也必须再次校验，不能只依赖 Renderer 状态。

### 8.2 与普通聊天冲突

第一版建议遵循单回合规则：

- 普通用户输入或 Agent 普通回答正在进行时，讲解按钮返回 `busy`；
- 讲解播放期间，用户可以停止当前讲解；
- 停止讲解不能关闭整个 Agent 输出，也不能影响下一轮普通聊天；
- 不支持讲解和普通回答同时播放；
- 不支持多个讲解排队。

### 8.3 取消和超时

每次讲解应有独立的请求 ID 和取消控制。至少覆盖：

- 用户重复点击；
- 用户点击停止；
- Agent 房间断开；
- 探索结果已过期；
- LLM 或 TTS 超时；
- 当前会话结束。

取消后，未完成的讲解不能继续回写聊天，也不能在旧请求结束后恢复播放。

## 9. 失败行为

- 探索结果不存在或已过期：提示用户重新执行探索；
- 探索快照没有可用讲解内容：说明当前探索内容不足，不编造内容；
- 百科或视频来源卡片缺失、打不开或只有搜索页：不单独触发内容抓取，只要探索快照仍有可用内容，就不阻塞讲解；
- LLM 失败：不影响已展示的探索卡片、普通聊天和手动探索；
- TTS 失败：保留讲解文字，并提示用户可以阅读文字；
- Agent 未连接：讲解文字可以根据产品实现选择保留为待发送状态或直接失败，但不能声称已播放；
- 用户在播放中点击停止：讲解消息保留，因为它已经是一次真实的 assistant 输出；
- 讲解失败：不得写入一条看似成功的 assistant 消息。

## 10. 不包含

- 后台监听飞机位置；
- 进入新地点后自动触发；
- 全局“自动导游”开关；
- 10 公里位置阈值和地点去重；
- 自动打开百科或视频来源窗口；
- 自动连续播放多个讲解；
- 自动读取任意百科网页全文；
- 讲解 AI 的独立长期记忆；
- 创建第二个 LiveKit AgentSession；
- 改变普通聊天消息、`guide.sources` 或现有探索 Provider 的语义。

## 11. 验收标准

### 探索与讲解

- 探索成功后，界面能提供讲解入口；
- 点击讲解只使用对应的 `explorationId` 和讲解范围；
- 同一主题可以由用户主动再次讲解，不按地理位置去重；
- 讲解只使用 `ExploreService` 已保存的探索快照内容，不重新读取百科或视频网页；
- 来源卡片缺失或网页无法打开时不会触发补抓取，探索内容不足时不会编造具体事实。

### 聊天展示

- 聊天面板对渲染高度超过约 6 行正文的 assistant 消息默认提供折叠预览；
- 未超过统一预览高度的普通回答不显示额外的展开/收起控制；
- 探索讲解与普通 assistant 消息使用相同的折叠、展开和收起逻辑；
- 折叠预览基于渲染后的 Markdown 高度，不通过字符串截断生成；
- 折叠不会截断聊天历史、Agent `ChatContext` 或后续追问可用的消息内容；
- 折叠或展开不会停止正在播放的讲解音频。

### 聊天上下文

- 讲解文字显示为当前聊天中的 assistant 消息；
- 讲解消息进入当前 Agent 的 `ChatContext`；
- 用户随后可以引用“刚才的讲解”继续提问；
- 讲解控制事件不会显示为虚假的用户消息；
- 讲解消息不会被错误包装成 `guide.sources`。

### 音频

- 讲解使用当前语言和当前 TTS 音色；
- 讲解音频复用现有 LiveKit/TTS 管线；
- 用户可以停止当前讲解；
- 停止讲解后，普通聊天仍能正常输入、回答和播放；
- TTS 失败时文字仍可见，且不会伪称播放成功。

### 稳定性

- 双击或重复请求不会产生两条讲解；
- 普通回答进行中不会出现音频重叠；
- 探索结果过期时不会讲解错误主题；
- Agent 断线后旧讲解不会回写到新会话；
- 讲解失败不会阻塞后续普通聊天和手动探索。

## 12. 建议测试

- 探索结果 ID 和主题 ID 校验；
- 只读取探索快照，不发起百科或视频内容读取，来源卡片元数据不作为事实上下文；
- 讲解文本长度和 locale 校验；
- 聊天面板新增的通用长消息规则：约 6 行阈值、默认折叠、展开/收起和短消息不显示控制；
- 折叠基于渲染高度而不是原始字符串截断，Markdown、链接和换行在展开后完整保留；
- 探索讲解与普通 assistant 消息的折叠行为一致；
- 讲解结果写入 assistant 上下文；
- 后续追问能够读取讲解内容；
- 重复点击和并发请求；
- 生成中取消、播放中停止；
- LLM 超时、TTS 失败、Agent 断线；
- 旧探索结果与新探索结果交叉点击；
- 讲解消息不污染 `guide.sources` 契约。

## 13. 待确认

1. 第一版范围已确定为“讲解本次探索总结”；按单个主题讲解作为后续扩展。
2. 探索快照缺少 `introduction` 时，是否允许基于主题标题和主题说明生成讲解？建议允许；如果这些字段也不足，则直接失败，不通过抓取百科网页补足。
3. 讲解完成后是否在消息上显示“探索讲解”标记？建议保留内部 `origin`，界面只做轻量标记。
4. 讲解播放中用户开始说话时，是否自动停止讲解？建议用户输入优先，停止当前播放，但保留已经写入的 assistant 消息。
5. 讲解文字是否进入后续手动探索的最近对话上下文？建议进入，但保留 `origin` 供后续裁剪和诊断。
