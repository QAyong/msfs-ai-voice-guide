# Spec-024：巡航阶段自动驾驶管理

**状态：** 已实现，已完成受控实机验证，仍属于安全实验功能
**建议优先级：** P1，本周最后处理
**目标周期：** 第一版已完成；后续按机型补充验证资料

## 当前实现与验证结果

这份需求的第一版已经落地。自动驾驶控制走 Native SimConnect，不走 EFB 的 WASM 航路桥；WASM 只负责读取 EFB 航路。

当前已经实现：

- 新增高层 `setAutopilot` 工具，只接受白名单参数；
- AP、FD、HDG、NAV、ALT、VS、FLC 及高度、航向、速度、垂直速度目标设置；
- 写入前读取当前飞机能力，写入后逐步读取实际状态；
- 官方 Key Event 作为模式控制路径，Input Event 只作为已验证的机型专用 AP/FD 兜底；
- 当前飞机不支持自动驾驶或能力未知时，不发送写事件；
- 每一步失败或读回不一致时停止，不把“事件已发送”说成“模式已生效”。

已完成验证：

- `C172SP G1000 Cargo`：AP、FD、HDG、ALT、VS 正负值、FLC、NAV、HDG+ALT 组合全部通过；
- `Asobo TBM 930 Passengers`：上述全量测试全部通过；
- `North American T-6 Texan Reno`：`AUTOPILOT AVAILABLE=0`，所有自动驾驶能力判定为不支持，调用被拒绝且没有发送写事件；
- 单元测试：214 个通过，8 个跳过；TypeScript 类型检查通过。

能力状态仍以当前飞机的运行时状态为准，不代表所有 MSFS 飞机都具备相同模式。Input Event 的具体名称和值属于机型行为，不能当作所有飞机的通用规则。

## 目标

用户明确要求后，AI 可以在巡航阶段管理当前飞机支持的自动驾驶模式和目标参数，并在操作后读取实际生效状态。

第一版的重点不是让 AI 持续操纵飞机，而是把用户明确说出的巡航设置转换为少量、受控、可验证的模拟器操作。

## 第一版范围

第一版支持以下能力，实际可用项必须以当前机型的能力检测结果为准：

- 自动驾驶 AP 和飞行指引 FD 的打开/关闭；
- 横向模式：HDG 航向模式、NAV 导航模式；
- 纵向模式：ALT 高度保持、VS 垂直速度、FLC 高度层改变；
- 设置目标高度、目标航向和目标速度；
- 读取当前活动模式、预位模式和实际目标值，并向用户报告。

### EFB 目标驱动

第一版的主要用户入口是：“按照 EFB 的目标，帮我设置自动驾驶。”

处理流程：

```text
读取 EFB 航路和目标高度
  → 读取当前飞机状态和自动驾驶状态
  → 判断当前机型支持的模式
  → 判断用户是否已经明确要求执行
  → 必要时询问缺失信息或歧义
  → 执行自动驾驶设置
  → 重新读取并报告实际状态
```

规则：

- EFB 有可用航路时，优先使用 NAV 跟随航路，不自动改为 HDG；
- EFB 有目标高度时，可以将其作为自动驾驶目标高度；
- EFB 没有目标高度时，不猜测高度，只执行能够确定的设置，或提示用户补充；
- EFB 没有速度目标时，不修改当前速度；
- 飞机正在爬升或下降时，优先保持当前可用的 VS 或 FLC 垂直模式，不擅自替用户切换；
- EFB 航路、目标参数或飞机状态读取失败时，不执行依赖这些数据的写操作；
- EFB 只提供目标来源，本需求不包含航路编辑、航路重算或自动选择备用航路。
- “按照 EFB 的目标，帮我设置自动驾驶”属于明确的执行指令；读取到的目标完整且机型能力明确时，可以直接执行，不要求额外二次确认；
- “自动驾驶应该怎么设置”或“看看能不能按 EFB 设置”属于询问或探索，不执行写操作，只提供建议或说明可执行方案；
- 用户只表达部分目标、参数之间存在冲突、或系统需要猜测关键设置时，先询问用户，不执行写操作。

示例：

> “EFB 航路是北京到上海，目标高度 8000 英尺。我准备接通自动驾驶，使用 NAV 跟随航路，并将目标高度设为 8000 英尺，不修改当前速度。要执行吗？”

### Agent 工具设计

第一版只需要两个工具配合完成这条流程：

- `getRouteBrief`：现有只读工具，负责读取 EFB Planned Route、出发地、目的地、程序、巡航高度和航路点；
- `setAutopilot`：新增写工具，负责按照用户明确要求的设置操作自动驾驶，并在操作后重新读取状态。

Agent 不直接调用 `simvar set`、`key-event send` 或 `input set`。这些底层能力由 `setAutopilot` 内部按照白名单映射使用。

`setAutopilot` 只接受固定的高层参数，未提供的参数保持当前状态，不主动修改：

```ts
{
  ap?: boolean,
  fd?: boolean,
  lateralMode?: 'HDG' | 'NAV',
  verticalMode?: 'ALT' | 'VS' | 'FLC',
  targetAltitudeFeet?: number,
  targetHeadingDegrees?: number,
  targetSpeedKnots?: number,
  targetVerticalSpeedFpm?: number,
}
```

参数规则：

- `NAV` 用于跟随 EFB 航路；没有可用 EFB 航路时不能设置 `NAV`；
- `ALT` 应与 `targetAltitudeFeet` 一起使用；
- `VS` 应与 `targetVerticalSpeedFpm` 一起使用；
- `FLC` 应与 `targetSpeedKnots` 一起使用；
- 没有 EFB 速度目标或用户没有明确提出速度时，不传入 `targetSpeedKnots`；
- 航向参数限制在 0 到 360 度，并按模拟器要求归一化；
- 不接受任意事件名、SimVar 名称、Input Event Hash 或原始数值指令。

工具调用顺序：

```text
用户提出要求
  → Agent 调用 getRouteBrief 读取 EFB
  → Agent 读取当前状态并检查机型能力
  → 判断用户是否已经明确要求执行
  → 不明确时询问；明确时直接执行
  → Agent 调用 setAutopilot
  → setAutopilot 检查机型能力并执行白名单操作
  → setAutopilot 重新读取状态并返回结果
```

`setAutopilot` 的执行顺序由服务层控制：需要时先接通 AP/FD，再切换横向或纵向模式，最后设置目标值；某些飞机在切换 VS 等纵向模式时会重置目标值，因此不能固定先写目标再切模式。每一步都要记录结果并读回实际状态。某一步失败或读回不一致时停止后续操作，并返回实际已经生效的状态，不声称整组操作成功。

`setAutopilot` 不需要额外的 `confirmAutopilot` 或 `cancelAutopilot` 工具。Agent 根据用户原话判断是否已经明确表达执行意图：明确指令可以直接调用；询问、建议、模糊指令或缺少关键参数时不得调用。

### 机型能力检测与不支持处理

`setAutopilot` 不能默认当前飞机有自动驾驶。写入前必须先判断当前机型和具体模式的能力。每项能力至少分为三种状态：

- `supported`：已经确认支持，可以执行；
- `unsupported`：已经确认不支持，不执行；
- `unknown`：无法可靠判断，按不支持处理，不执行。

能力判断应结合当前飞机标识、已验证的机型能力资料和运行时可读取的状态，不能只依靠模型猜测或只看飞机名称。第一版优先维护已验证机型的能力资料；没有资料或资料与运行时状态不一致时，返回 `unknown`。

处理规则：

- 当前飞机没有自动驾驶时，返回明确的“不支持自动驾驶”结果，不发送任何写事件；
- 当前飞机有自动驾驶，但不支持请求中的某个模式时，拒绝该模式；
- 同一请求包含多个设置且只有部分支持时，不静默执行支持的部分，先向用户说明可执行的简化方案，并重新取得确认；
- 无法判断自动驾驶或模式是否支持时，不进行试探性写入；
- 自动驾驶不支持时，`getRouteBrief` 等 EFB 只读能力仍然可以继续使用。

示例：

> “当前飞机没有可用的自动驾驶，模拟器状态没有被修改。EFB 航路仍然可以读取，但需要手动操纵。”

> “当前飞机支持自动驾驶，但不支持 NAV 跟随航路。我暂时没有执行设置，可以改用 HDG 航向模式。”

第一版暂不支持：

- LOC、APR、GS 等进近模式；
- 自动油门、FMS Managed Mode 或其他机型专用管理模式；
- 高频姿态、油门或方向舵控制。

## 操作流程

```text
用户提出操作
  → Agent 调用只读工具获取当前目标和状态
  → 判断用户是否明确要求执行
  → 不明确：询问或说明方案并停止
  → 明确：Agent 调用 `setAutopilot`
  → 读取结果
  → 告知成功或失败
```

用户没有明确表达执行意图时，不执行任何写操作。明确指令只覆盖其中已经确定的操作；新增或改变操作目标时，需要用户重新明确提出，或在存在歧义时先询问。

## 当前基础

- Native CLI 已有 `simvar set`、`key-event send` 和 `input set`。
- 写操作当前要求显式 `--unsafe`。
- 当前 Agent 已有 `getRouteBrief` 和 `setAutopilot`；`setAutopilot` 负责能力检查、白名单映射、执行和结果验证。
- 自动驾驶模式和目标值需要通过受控的高层语义映射到白名单事件或 SimVar，不能把 CLI 的任意写入能力直接暴露给模型。

## 安全规则

- 新增独立的“允许飞机操作”设置；
- 只允许白名单操作，不能让模型直接提交任意 SimVar 名称、Key Event 名称或 Input Event Hash；
- 明确、完整、可执行的用户指令可以直接触发写入，不强制要求额外二次确认；
- 用户只是在询问、请求建议、缺少关键参数或表达存在歧义时，不执行写入；
- 写入后必须重新读取状态；
- MSFS 未连接、变量不可写或机型不支持时，不执行并返回原因；
- 当前飞机没有自动驾驶、具体模式不支持或能力未知时，不擅自执行替代操作；
- 不得把未生效的预位模式表述为已接通的活动模式；
- 同一请求包含多个设置时，必须逐项记录执行结果；部分成功时必须明确列出成功项和失败项；
- 不做高频姿态、油门或方向舵闭环控制；
- 不做自动起飞、自动降落或全自动飞行。

## 验收标准

- 没有明确执行意图时，任何操作都不会改变模拟器状态。
- 用户明确要求后，在支持的机型上可以执行 AP/FD、HDG/NAV、ALT/VS/FLC 及目标高度、航向、速度设置。
- 用户要求“按照 EFB 的目标设置自动驾驶”时，系统能读取 EFB 航路和目标高度，生成准确的执行方案。
- Agent 先调用 `getRouteBrief`，只有在用户明确要求执行时才调用 `setAutopilot`。
- `setAutopilot` 只接受白名单参数，省略的目标值不被修改，且不能接收任意底层写入参数。
- EFB 有航路时，执行后能使用 NAV 跟随航路；EFB 缺少目标高度或速度时，不会擅自猜测或修改对应参数。
- 操作后能读取并展示实际活动模式、预位模式和目标值；不能把仅发送成功的事件当作状态已生效。
- 操作失败时返回明确错误，不声称成功。
- 对不支持的模式或目标参数，在写入前明确提示并不执行该项。
- 对没有自动驾驶的飞机，系统能明确提示“不支持自动驾驶”，且模拟器状态保持不变。
- 对只支持部分模式的飞机，系统能拒绝不支持的模式，不静默执行未经重新确认的简化方案。
- 对能力未知的飞机，系统不进行试探性写入，并明确提示尚未验证。
- 只读工具、语音会话和 MSFS 连接监控不受影响。
- 至少使用一架支持自动驾驶的飞机，以及一架不支持自动驾驶或只支持部分模式的飞机完成实机验证。

## 后续工作边界

第一版已经完成受控验证，但它仍然会改变模拟器状态，不能当作高频闭环飞行控制使用。后续如要扩大覆盖范围，应继续按机型补充能力资料和实机测试，不应把某一架飞机的 Input Event 名称或行为直接推广到所有飞机。
