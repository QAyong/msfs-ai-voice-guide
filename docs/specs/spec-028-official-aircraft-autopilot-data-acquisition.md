# Spec-028：官方飞机自动驾驶数据采集与验证

**日期：** 2026-09-10  
**状态：** 数据采集和测试工具已实现；白名单与双写入方式由 Spec-029 定义

## 1. 这份文档要解决什么问题

不同飞机的自动驾驶绑定方式不完全一样。

本文件只负责采集和验证官方飞机的自动驾驶能力，不负责定义运行时的写入路由。

当前项目不再尝试适配所有飞机，也不在运行时猜测飞机的写入方式。正式白名单以及每架飞机选择 Key Event 还是 Input Event，由 [Spec-029：官方飞机自动驾驶白名单与双写入方式](spec-029-official-aircraft-autopilot-write-methods.md) 定义：

```text
在白名单中 → 允许使用当前项目的通用自动驾驶写入
不在白名单中 → 直接告诉用户：当前飞机不适配
```

这份白名单是运行时是否允许自动驾驶写入的第一道门。

## 2. 采集结果如何进入白名单

028 的输出是证据，不是自动放行结果。采集结果经过人工审阅后，才可以写入 029 定义的唯一官方白名单。

采集结果主要包括：

- 飞机身份和版本；
- AP、FD、HDG、NAV、ALT、VS、FLC 的状态；
- Key Event 的写入和读回结果；
- Input Event 的名称、Hash、类型、参数、写入值和读回结果；
- 测试环境、失败原因和版本指纹。

029 再根据这些证据填写 `writeMethod`（`key_event` 或 `input_event`）以及 `supportedOperations`。

## 3. 哪些飞机可以进入名单

必须同时满足：

1. 飞机属于 MSFS 2024 官方飞机范围；
2. 飞机可以使用官方 Key Event 或官方 Input Event；
3. 选择的写入方式经过运行时写入和独立读回验证；
4. 项目能够稳定识别这架飞机。

以下飞机不进入白名单：

- Community 或其他第三方飞机；
- 没有自动驾驶的飞机；
- 只能依赖非官方接口、不可验证的专用插件或不受项目控制的写入方式的飞机；
- 尚未验证、版本不匹配或无法稳定识别的飞机。

官方 Input Event 不属于排除项。只要它符合官方 SimConnect API，并且已经完成逐机验证，就可以由 029 指定为该飞机的 `input_event` 写入方式。

这些情况不需要再分别维护多张“拒绝名单”。只要不在唯一白名单中，运行时就拒绝自动驾驶写入。

## 4. 与运行时的关系

```text
028 采集和验证
      ↓
人工审阅
      ↓
029 写入唯一官方白名单
      ↓
运行时匹配飞机并选择写入方式
```

运行时的详细白名单匹配和双写入方式见 029。白名单命中后仍然要做当前状态检查和写入后的独立读回。

## 5. 当前项目的自动驾驶采集范围

第一版只使用项目已经实现的通用操作：

- AP 开关；
- FD 开关；
- HDG 模式；
- NAV 模式；
- ALT 模式；
- VS 模式；
- FLC 模式；
- 航向、高度、速度和垂直速度目标值。

028 同时采集两类官方写入证据：Key Event 和 Input Event。哪一种方式最终用于某架飞机，由 029 的 `writeMethod` 决定，不在运行时自动猜测或自动切换。

项目不向 Agent 暴露原始 SimVar、Key Event 名称、Input Event Hash 或任意底层写入接口。

## 6. 028 的数据是怎么来的

### 6.1 官方飞机目录

从官方飞机包的 `manifest.json`、`aircraft.cfg`、包版本和文件指纹中读取飞机身份，区分官方飞机、官方合作方候选、第三方飞机和非目标版本。

当前目录代码为：

```text
src/msfs/official-aircraft-catalog.ts
```

### 6.2 当前飞机检查器

运行：

```text
pnpm msfs:inspect
```

检查器使用 `monitor` daemon，只读当前连接的模拟器状态，采集：

- 当前飞机身份；
- AP 相关 SimVar；
- 当前飞机的 Input Event 列表；
- Input Event 的参数和值；
- 可用的飞机目录。

结果保存到：

```text
docs/msfs/autopilot/inspections/
```

它不会切换用户飞机，也不会发送自动驾驶写入命令。

### 6.3 临时 AI 批量测试

运行：

```text
pnpm msfs:probe
pnpm msfs:probe:batch -- --batch-size 12
```

测试程序会：

1. 枚举官方飞机标题；
2. 创建临时非 ATC AI 飞机；
3. 读取 AP、FD、HDG、NAV、ALT、VS、FLC 状态；
4. 使用 `--modes` 时发送标准自动驾驶事件并读取结果；
5. 删除临时 AI 飞机。

结果保存到：

```text
docs/msfs/autopilot/runtime-probes/
```

这项测试只用于收集证据和回归验证。它不切换用户正在驾驶的飞机，因此测试结果不能单独证明用户飞机的专用控制路径已经适配。

## 7. 白名单的加入流程

```text
发现官方飞机
      ↓
确认使用 key_event 或 input_event
      ↓
测试实际写入和独立读回
      ↓
人工审阅测试结果
      ↓
加入 029 定义的唯一官方白名单
      ↓
运行时允许 setAutopilot 使用
```

探测工具产生的结果只是候选证据，不能自动把飞机加入正式白名单。

## 8. 白名单匹配规则

第一版使用以下信息匹配飞机：

- `packageName`；
- `aircraftTitle`；
- 必要时增加变体信息。

`ATC ID` 只能作为当前实例的辅助信息，不能作为飞机型号的唯一身份。

涂装不应改变飞机的适配结论。游戏版本或飞机包版本发生变化时，应重新验证白名单条目。

## 9. 用户提示

### 未命中白名单

```text
当前飞机不在项目官方自动驾驶适配名单中，暂不支持自动驾驶控制。
```

### 命中白名单但请求了未开放的操作

```text
当前飞机已适配，但暂不支持本次请求中的部分自动驾驶操作：NAV、FLC。
已支持的操作可以继续执行。
```

### 写入后读回失败

```text
自动驾驶指令已发送，但状态没有确认生效。已停止后续操作，请检查当前飞行状态。
```

## 11. 验收标准

- [ ] 项目只维护一份正式官方自动驾驶白名单；
- [ ] 白名单外的飞机不会发送自动驾驶写入命令；
- [ ] 每个白名单条目明确记录 `writeMethod`；
- [ ] 每个白名单条目只允许执行 `supportedOperations` 中的操作；
- [ ] 没有完成官方 API 验证的写入方式不会自动放行；
- [ ] 每个写入操作都有独立状态读回；
- [ ] 任一步读回失败，后续操作停止；
- [ ] 飞机包或游戏版本变化后，旧的验证结果不能直接视为永久有效。

## 13. 设计原则

```text
028 负责证明“这架飞机的写入方式可行”
029 负责决定“项目是否维护这架飞机、使用哪种写入方式”
运行时读回负责确认“这次操作是否真的生效”
```

三者不能混为一谈：

- 没有进入 029 白名单，不允许写入；
- 白名单指定哪种写入方式，就使用哪种写入方式；
- 操作不在 `supportedOperations`，不允许执行；
- 写入后读回失败，不能向用户报告成功。
