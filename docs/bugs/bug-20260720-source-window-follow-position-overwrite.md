# Bug：来源浏览窗不再跟随聊天面板

**日期：** 2026-07-20

**优先级：** 高

**状态：** 已修复

## 复现步骤

1. 展开聊天面板并打开任意一组网页来源，使伴随来源浏览窗出现。
2. 拖动聊天面板，或改变聊天面板尺寸。
3. 观察来源浏览窗的位置。

## 实际结果

聊天面板移动后，来源浏览窗仍停留在原处，没有重新定位到聊天面板旁；两个窗口之间的伴随关系丢失。

## 预期结果

来源浏览窗始终位于聊天面板内侧，并在聊天面板移动、缩放或跨显示器时同步重新定位；来源窗自身原来的坐标不得覆盖新计算的伴随坐标。

## 影响范围

- `desktop/main/index.ts` 中聊天面板移动、缩放和显示器变化触发的伴随定位。
- `desktop/main/window-placement.ts` 中来源浏览窗坐标计算。
- 多显示器、负坐标显示器以及用户调整过来源窗尺寸后的场景。

## 原因

`positionSourceNextToAssistant()` 把 Electron `BrowserWindow.getBounds()` 返回的完整来源窗边界对象传给只需要 `width`、`height` 的布局函数。TypeScript 的结构化类型允许该对象通过检查，但运行时对象仍含有旧的 `x`、`y`。

`placeCompanionWindow()` 在返回对象末尾展开该参数，导致已经计算好的新 `x`、`y` 被旧坐标覆盖，后续 `setPosition()` 实际上仍设置原位置。

## 修复方案

- 调用方只传入来源窗的 `width`、`height`，不把旧坐标带入布局函数。
- 布局函数先展开尺寸、最后写入新坐标，即使运行时意外收到完整边界对象，新坐标也拥有最终优先级。
- 增加传入完整 Electron 边界对象的回归测试，并进行真实 Electron 窗口移动验收。

## 修复结果

- `positionSourceNextToAssistant()` 现在只向布局函数传递来源窗宽高。
- `placeCompanionWindow()` 调整返回对象顺序，重新计算的 `x`、`y` 不会再被运行时额外字段覆盖。
- 单元测试先稳定复现旧坐标覆盖，再验证修复后得到正确的新坐标。
- 真实 Electron 验收中，聊天面板位移 `(-100, +50)` 后，来源浏览窗同步产生相同位移，两个窗口的伴随间距保持不变。
