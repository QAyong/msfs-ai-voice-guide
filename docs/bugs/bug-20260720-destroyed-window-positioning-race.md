# Bug：已销毁窗口仍参与伴随定位

**日期：** 2026-07-20  
**优先级：** 高  
**状态：** 已修复

## 复现步骤

1. 打开聊天面板和来源浏览窗。
2. 关闭来源浏览窗，或在聊天面板收起时触发来源窗同步关闭。
3. 在来源窗进入关闭阶段时展开聊天面板菜单、调整聊天面板尺寸，或触发窗口定位事件。

## 实际结果

Electron 主进程抛出 `TypeError: Object has been destroyed`（对象已经销毁），错误堆栈指向 `positionSourceNextToAssistant()`（把来源窗定位到聊天面板旁）和 `BrowserWindow.setBounds()`（设置窗口边界），并显示 JavaScript 主进程错误弹窗。

## 预期结果

窗口进入关闭或销毁阶段后立即退出所有移动、缩放、伴随定位和 IPC（进程间通信）操作；关闭来源窗不得影响聊天面板继续运行。

## 影响范围

- `desktop/main/index.ts`（Electron 主进程窗口编排）。
- 关闭来源窗、收起聊天面板、展开收起态菜单、调整聊天窗口和显示器变化等场景。
- 异常未被捕获时会向用户显示主进程错误弹窗，严重影响应用稳定性。

## 初步判断

`BrowserWindow.close()`（关闭窗口）到 `closed`（窗口已关闭）事件之间存在短暂窗口：全局 `sourceWindow`（来源窗口）仍非空，但底层原生对象已经不可用。现有保护只判断引用是否存在，没有同时调用 `isDestroyed()`（是否已销毁）；聊天面板同步触发的移动或缩放事件因此继续读取、移动已销毁窗口。

## 处理方式

- 提供统一的窗口存活判定，所有窗口边界、显示、关闭和发送操作必须先通过该判定。
- 在 `close` 阶段而不是等待 `closed` 事件才释放全局来源窗口引用。
- 事件回调捕获创建时的窗口实例，避免旧窗口的延迟事件清空后来创建的新窗口。
- 增加窗口生命周期单元测试和真实应用重启验证。

## 修复结果

- 新增 `isLiveWindow()`（判断窗口是否仍存活），在读取边界、移动、缩放、显示、关闭、IPC 发送和持久化前统一拦截已销毁窗口。
- 来源窗在 `close`（开始关闭）事件中立即释放全局引用和网页视图，不再等待 `closed`（关闭完成）事件。
- 聊天窗、来源窗和工具窗的事件回调均捕获创建时实例；旧窗口的延迟事件不会清除后来创建的新窗口。
- 真实 Electron 回归按“创建来源窗 → 关闭来源窗 → 立即改变聊天窗边界”的顺序执行，应用保持运行且未出现 Error 窗口。
- `tests/unit/window-lifecycle.test.ts` 覆盖存活、已销毁、原生查询抛错和旧窗口延迟释放四类边界。
